ADR-0006…0008 · Work-type needs filter (sprint 002)

3 decisionsacceptedsubsystem N/Aupdated 2026-09-29

Overview

This sprint adds a WorkManager-local needs filter to work-type assignment rules. Three decisions cover it: the data model and needs check (ADR-0006), the absolute block in the dedicated-worker fail-safe (ADR-0007), and the settings UI, rule summary and localization (ADR-0008).

Design background: the RimWorld 1.6 needs research (Need / NeedDef / pawn.needs API, CurLevelPercentage semantics, Outdoors and Beauty levels, thoughts and mood effects, related mods) is in audit.md, "Background research" R-1…R-8 (AC-45). It is marked for promotion to design/architecture/tech-reference/RimWorld-1.6.md at design-promote.

Inputs: prd.html (49 ACs, decisions D1–D9), audit.md (gaps G-1…G-7), .asd/project/decisions-log.md (2026-09-29: scope decisions, G-3 option (a), no hysteresis).

ADR-0006 · WorkManager-local needs filter on WorkTypeAssignmentRule

Context

  • Scope decisions (decisions-log 2026-09-29): a per-work-type needs filter that is WorkManager-local, because LordKuper.Common is an upstream contract and cannot be edited from this repo. It blocks strictly below a threshold, supports any need, ships no defaults, and the block is absolute. There is no hysteresis: the check is stateless and runs on every update.
  • The existing rule model is WorkTypeAssignmentRule : DefCache<WorkTypeDef>, IExposable. Nullable fields mean "undefined, inherit from the default rule". Combine(main, fallback) takes the value from main when it has one. Validate() runs only when saving. Settings load in the WorkManagerMod constructor, before defs are loaded.
  • Common precedent: PawnCapacityLimit : DefCache<PawnCapacityDef>, IExposable together with PawnFilter.FilterPawnCapacities (bool?) and PawnCapacityLimits (list). CombinePawnCapacities takes the source whose flag has a value and makes a shallow copy of its list. SatisfiesFilter skips entries whose def is unresolved and keeps no state.
  • DefCache<T> resolves lazily through DefProvider.Current.GetNamedSilentFail<T>. It latches on the first .Def / .Label read, so reading either before defs load caches null until restart.
  • Scribe_Collections.Look(..., LookMode.Deep) sets the list to null when the node is missing, which is the case for settings saved by older versions.
  • Convention conflict D-3: LordKuper.Common-1.6.md states "Pawn eligibility is expressed through PawnFilter … not ad-hoc predicates".
  • Evaluation choke point: PawnCache.IsAllowedWorker(WorkTypeDef) calls CombinedRulesDict[wt].IsAllowedWorker(pawn). The result is memoised per update and cleared on every refresh.
  • Tests target net472 with NUnit 4.6.1 and FluentAssertions 7.2.2. No existing test constructs a Pawn. Common exposes DefProvider.Current (a public, settable IDefProvider) as the def-lookup seam. Common's own tests construct defs with object initialisers.

Decision

Add a NeedLimit entry type and a tri-state needs filter to WorkTypeAssignmentRule, following the shape of Common's capacity limits. Evaluate it inside IsAllowedWorker through a pure static seam.

  1. Entry type. New internal sealed class NeedLimit : DefCache<NeedDef>, IExposable in Source/WorkManager/Settings/NeedLimit.cs.
    • Field: public float Threshold = DefaultThreshold; with internal const float DefaultThreshold = 0.5f (AC-32). It is stored as a fraction in [0, 1], the same scale as Need.CurLevelPercentage, and shown as 0–100%.
    • Constructors: NeedLimit() for Scribe, NeedLimit(string defName) and NeedLimit(NeedDef def).
    • public new void ExposeData() { base.ExposeData(); Scribe_Values.Look(ref Threshold, nameof(Threshold), DefaultThreshold); }. Only the defName and threshold are persisted, never Scribe_Defs / LookMode.Def (AC-11). Unresolved defNames survive load and save (AC-12).
  2. Rule fields (after AllowedWorkers): public bool? FilterNeeds; (null = Inherit, false = Off, true = On) and public List<NeedLimit>? NeedLimits = [];. The list is nullable because Scribe can set it to null on load (AC-1).
  3. Persistence. ExposeData adds Scribe_Values.Look(ref FilterNeeds, …) and Scribe_Collections.Look(ref NeedLimits, …, LookMode.Deep), followed by if (Scribe.mode == LoadSaveMode.LoadingVars) ValidateNeedsFilter();. ValidateNeedsFilter reads only DefName and Threshold, so it is safe before defs load (AC-10, AC-11). Settings_Version is not bumped: the nodes are additive and optional.
  4. internal void ValidateNeedsFilter(), also called from Validate() on every save:
    • Sets NeedLimits ??= [] and drops null entries and entries with an empty DefName.
    • Removes duplicate DefNames (OrdinalIgnoreCase) and keeps the first (AC-3).
    • Clamps Threshold with Mathf.Clamp01 (AC-2).
    • On the default rule (DefName == null), sets FilterNeeds ??= false (AC-4).
    The method is internal because Validate() reads WorkManagerMod.Settings, which is not available in unit tests.
  5. Construction. CreateRule(defName) sets FilterNeeds = defName == null ? false : null and NeedLimits = [] (AC-4, AC-5). In DefaultRules, the default rule sets FilterNeeds = false explicitly. No shipped rule has entries or FilterNeeds == true (AC-6).
  6. Combine. var source = main.FilterNeeds.HasValue ? main : fallback; then FilterNeeds = source.FilterNeeds; NeedLimits = [.. source.NeedLimits ?? []];. This is a shallow copy, the same as PawnFilter.CombinePawnCapacities (AC-7, AC-8).
  7. Evaluation.
    • IsAllowedWorker(pawn) becomes AllowedWorkers!.SatisfiesFilter(pawn, Def) && !IsNeedBlocked(pawn) (AC-20).
    • internal bool IsNeedBlocked(Pawn pawn) => IsNeedBlocked(FilterNeeds, NeedLimits, def => pawn.needs?.TryGetNeed(def)?.CurLevelPercentage); is a one-line call into the static seam, which is the only place that checks the state.
    • Pure test seam: internal static bool IsNeedBlocked(bool? filterNeeds, IReadOnlyList<NeedLimit>? limits, Func<NeedDef, float?> getLevelPercentage).
      • Returns false when the state is not On or the list is empty (AC-19).
      • Skips entries whose Def == null (AC-18).
      • Skips a null level: the pawn lacks the need (AC-16) or pawn.needs == null (AC-17).
      • Blocks when level < Threshold for any entry. The comparison is strict: a level equal to the threshold passes (AC-14), and a 0% threshold never blocks (AC-15, AC-13).
      • Keeps no state between updates (AC-21).
    • CurLevelPercentage is used rather than CurLevel because Food and MechEnergy have MaxLevel != 1 (audit R-1).
    • PawnCache is unchanged. It memoises the verdict per update and recomputes it on every update (AC-22, AC-23). Priority 0 is already the default outcome of UpdateCache, so no new write path is needed.
  8. Scoped exception to the eligibility convention (D-3). Pawn eligibility stays expressed through PawnFilter, except for this per-work-type needs filter on WorkTypeAssignmentRule. At design-promote, the convention line in LordKuper.Common-1.6.md is amended to cite ADR-0006. If Common later adds a needs dimension to PawnFilter, a new ADR supersedes this one and migrates the settings.
  9. Test approach (net472, no Pawn construction).
    • A new test-only FakeDefProvider : IDefProvider in WorkManager.Tests (dictionary-backed). It is installed into DefProvider.Current in SetUp and restored in TearDown. Fixtures that touch default-rule caches derive from StateIsolationTestBase.
    • NeedDefs are built with new NeedDef { defName = …, label = …, listPriority = … }. If that needs the game runtime, the fallback is FormatterServices.GetUninitializedObject plus field assignment (the IsInitializedTests precedent).
    • The need-level check is tested through the static IsNeedBlocked with a dictionary-backed getLevelPercentage. A missing key means the pawn lacks the need; all-null values mean pawn.needs == null. This covers AC-13…AC-19.
    • ValidateNeedsFilter tests cover AC-2, AC-3, AC-4 and AC-10 (older settings simulated by setting the fields to null). DefaultRules tests cover AC-6, and Combine tests cover AC-7 and AC-8.
    • The real Scribe round trip (AC-9, AC-11, AC-12) and the one-line pawn.needs? adapter (AC-17) are manual in-game checks, following the sprint 001 MS precedent.

Consequences

Positive

  • Same shape as the existing tri-state rule fields and Common's capacity limits, so the code is familiar to reviewers.
  • Safe with older settings (the list is null-coalesced on load) and with removed DLCs or mods (entries are kept and skipped).
  • One evaluation point covers every gated assignment pass. The result is memoised per update, and the cost is negligible: a few linear TryGetNeed scans, made only while the state is On. The level-lookup delegate is allocated on every call (memoised per update), which is negligible.
  • The pure static seam makes AC-13…AC-19 unit-testable without building Pawn object graphs.

Negative

  • There are now two eligibility mechanisms, which is a documented exception to a project convention. The "Available pawns" preview and DedicatedWorkerMode.PawnCount target counting do not see the needs filter.
  • Combined rules share NeedLimit instances with the source rule (shallow copy, as in Common). Edits in the settings window reach the combined rule before WriteSettings rebuilds it.
  • Unresolved entries are silently inert during evaluation. The only signal is the marker in the UI (ADR-0008).
  • The pawn.needs?.TryGetNeed adapter line and the Scribe round trip are not unit-tested; they are covered by manual checks.
  • Fast-changing needs (Beauty, Comfort, Food, Rest, Mood) can switch a work type on and off between updates. This is accepted by user decision (no hysteresis); the tooltip gives guidance.
  • Any future code that reads .Def / .Label of a NeedLimit on the load path would silently break def resolution until restart.

Alternatives considered

  • Persisted NeedDef → float dictionary, rejected because it needs LookMode.Def or manual key lists, breaks loading before defs, and diverges from Common's limit pattern.
  • FloatRange per need (like PawnCapacityLimit), rejected because the scope is a lower threshold only. A range doubles the UI and the semantics with no requirement behind it.
  • A separate NeedsFilter sub-object, rejected because it adds a layer for two fields when the rule already hosts sibling tri-state fields.
  • A needs dimension in Common's PawnFilter, rejected because Common is not editable from this repo (non-goal).
  • A per-entry predicate (float? level, float threshold) as the only seam, rejected because it leaves the aggregation loop untested: the any-entry rule, the unresolved skip and the state gating.
  • Real Pawn / Pawn_NeedsTracker objects built through GetUninitializedObject and reflection, rejected as brittle against game internals (audit G-7).

  • ADR-0008: the UI, summary and strings for these fields.

ADR-0007 · Needs block is absolute in the day-level dedicated-worker fail-safe

Context

  • In WorkPriorityUpdater.AssignDedicatedWorkersForDay, after the pass that assigns from goodWorkers, a fail-safe builds availableWorkers from all _capablePawns that are not in goodWorkers. That includes pawns that fail IsAllowedWorker. The fail-safe tries to reach max(target, MinWorkerNumber) when EnsureWorkerAssigned is set.
  • The fail-safe runs when schedule-aware selection is off, or when no allowed worker has a Work hour. The rule there is the combined rule (_managedWorkTypeRules, built from CombinedRules).
  • User decision G-3 (a), 2026-09-29: exclude only need-blocked pawns, and keep the fail-safe's existing AllowedWorkers behaviour identical (AC-24, AC-26). Option (b) is a follow-up.

Decision

Only the fail-safe's candidate loop changes: if (!goodWorkers.Contains(pc) && !rule.IsNeedBlocked(pc.Pawn)) availableWorkers.Add(pc);

  • IsNeedBlocked(Pawn) is the ADR-0006 instance method on the combined rule. It is not memoised, because the fail-safe runs rarely.
  • A code comment states that the fail-safe excludes need-blocked pawns only and deliberately does not apply AllowedWorkers (follow-up G-3 (b)).
  • No other path changes. Every other pass already goes through PawnCache.IsAllowedWorker, which now includes the needs check (AC-22, AC-25). When every eligible pawn is need-blocked, fewer workers are assigned, possibly none (AC-25).
  • Compatibility shims (WorkTab, PriorityMaster, MoreThanCapable): no new priority-write path. Priority 0 goes through the existing WorkTypePriorityHelper.SetPriority, so the shims are not affected.

Consequences

Positive

  • The absolute block holds on every assignment path, with a one-condition change.
  • With the filter Off or empty, IsNeedBlocked returns false before it touches the pawn. The candidate set and the resulting priorities are identical to the previous version (AC-26).

Negative

  • The fail-safe still bypasses AllowedWorkers and Pawn.WorkTypeIsDisabled. This pre-existing latent issue is knowingly left in place, so the two filters behave differently in this branch.
  • EnsureWorkerAssigned can now leave a work type with no workers. This is intended; the tooltips are reworded in ADR-0008.
  • AC-24 is verified by review and a manual in-game check, not a unit test. The candidate selection needs map and pawn state.

Alternatives considered

  • G-3 (b): restrict the fail-safe to allowedWorkers, rejected for this sprint by user decision because it changes existing behaviour (AC-26).
  • Memoise the need-blocked verdict on PawnCache, rejected because it adds state for a rarely run path (Simplicity Default).
  • Extract the candidate selection into a static helper for unit tests, rejected because it adds a new seam in a map-coupled method for a single condition.

Related ADRs

  • ADR-0006: defines IsNeedBlocked(Pawn).
  • ADR-0008: EnsureWorkerAssigned / MinWorkerNumber tooltip rewording.

ADR-0008 · Needs section, rule summary and localization, built from Common's public API only

Context

  • The settings UI is RimWorld IMGUI composed from Common primitives. The UX-spec step was skipped (see the PRD Design context), so AC-27…AC-41 are the UI specification.
  • Some helpers used by Common's own capacity-limits section are internal: Sections.DoToggleableSectionHeader, Resources.Textures.Actions.Delete (an alias of vanilla TexUI.DismissTex), Layout.DoVerticalGapSmall, PawnCapacityLimit.ValueStep and Fields.GetFloatSliderStepByValueStyle.
  • These are public:
    • Sections and fields: Sections.DoLabeledSectionBox, Fields.DoLabeledCheckbox(ref bool) / (ref bool?), Fields.DoLabeledPercentSlider.
    • Buttons, labels and layout: IconButton, Buttons.DoActionButton, Labels.DoLabel, Layout.GetTopRowRect.
    • Defs: DefHelper.GetLabel, DefProvider.Current.
    • Strings: Common.Resources.Strings.Actions.Add / .Delete.
  • The rule editor already shows tri-state fields as Fields.DoLabeledCheckbox(ref bool?) rows on work-type rules and ref bool rows on the default rule. Their tooltips come from Get*Tooltip(bool triState) plus AppendUndefinedSettingTooltip.
  • Keys: each 1.6 locale (en, ru, zh-Hans) has the same 47 LordKuper.WorkManager.Settings.WorkTypes.* keys. The legacy 1.1–1.5 folders have none.

Decision

Build the Needs section only from Common's public helpers and vanilla widgets. Add a Needs part to the rule summary, add 8 new keys and reword 3 existing ones in the three 1.6 locales.

  1. Settings_WorkTypes.DoRuleNeeds(Rect rect, bool defaultRule, out Rect remRect), called in DoWorkTypeRule right after DoRuleAllowedWorkers (AC-27).
    • A new cached field _needsSectionContentHeight is updated on EventType.Layout. No input-id constants are needed.
    • The section box is Sections.DoLabeledSectionBox(..., Strings.NeedsLabel, Strings.NeedsTooltip, ...). NeedsTooltip makes the four AC-37 statements.
    • State row, default rule: Fields.DoLabeledCheckbox(ref bool) with GetFilterNeedsTooltip(false) (Off / On).
    • State row, work-type rule: Fields.DoLabeledCheckbox(ref rule.FilterNeeds) with GetFilterNeedsTooltip(true). The Partial state uses the existing undefined-setting wording (AC-28, AC-29).
    • With state On and no entries, a Labels.DoLabel row shows Strings.NeedsEmptyLabel (AC-36).
    • Each entry: Fields.DoLabeledPercentSlider(rect, 1, [new IconButton(TexUI.DismissTex, remove, Common.Resources.Strings.Actions.Delete)], label, tooltip, ref limit.Threshold, 0f, 1f, 0.01f, null, out rect) (AC-33, AC-34).
      • Resolved entry: label limit.Label, tooltip limit.Def.description.
      • Unresolved entry: label string.Format(Strings.NeedUnavailableLabel, limit.DefName), tooltip Strings.NeedUnavailableTooltip. It uses the same row layout and can be removed (AC-35).
      • Removal follows Common's deferred-index pattern.
    • Add button: Buttons.DoActionButton(rect, Common.Resources.Strings.Actions.Add, ...), shown only while an addable need exists. It opens a vanilla FloatMenu with one FloatMenuOption per addable need, labelled def.GetLabel(). Choosing an option adds new NeedLimit(def) at 50% (AC-30, AC-32). The button reads Common's "Add"; this was a user decision on 2026-09-29, so there is no "Add need" key.
    • Option tooltip (AC-31): def.description goes in FloatMenuOption.tooltip. That field is not yet verified in the 1.6 Assembly-CSharp. Fallback: if it is missing, show the description through the option's mouseoverGuiAction with TooltipHandler.TipRegion. Either way, no new dependency.
    • Addable needs: internal static List<NeedDef> GetAddableNeeds(IEnumerable<NeedDef> all, IReadOnlyCollection<NeedLimit> existing), fed from DefProvider.Current.AllDefsListForReading<NeedDef>().
      • Excludes playerMechsOnly needs, defName == "Authority" and defNames already present (OrdinalIgnoreCase).
      • Includes needs with showOnNeedList == false.
      • Sorts by listPriority descending, then by label (CurrentCulture).
    • Changes take effect through the existing WriteSettings → UpdateSettingsCache → ForceUpdateAssignments flow (AC-38).
  2. Internal Common helpers, and how they are replaced:
    • DoToggleableSectionHeader: not needed, because the editor uses checkbox rows for tri-state fields.
    • Textures.Actions.Delete: replaced by vanilla TexUI.DismissTex, the texture it aliases.
    • DoVerticalGapSmall and the slider step helpers: not needed. The step is the literal 0.01f required by AC-33; it is a UI step, not a balance tunable.
    • No reflection into Common.
  3. Rule summary (Description). After the Allowed workers part: a coloured Strings.NeedsLabel header at indent 1, then at indent 2:
    • Inherit: WorkTypeRuleUndefinedSectionTooltip.
    • Off: WorkTypeRuleDisabledSettingTooltip.
    • On with no entries: NeedsEmptyLabel.
    • On: one line per entry, "<label>: <Threshold.ToStringPercent()>", using the defName when the entry is unresolved (AC-39).
    The summary is only read at UI time, after defs load, so the DefCache latch is safe.
  4. Strings. New members in Resources.Strings.Settings.WorkTypes, keyed LordKuper.WorkManager.Settings.WorkTypes.<Name> (AC-42). The keys go in the 1.6 English, Russian and ChineseSimplified WorkManager_Keyed.xml only (AC-43, AC-44). The Russian and ChineseSimplified values are real translations, not English placeholders (AC-49, PRD D5).
    • 8 new keys: NeedsLabel, NeedsTooltip, FilterNeedsLabel, FilterNeedsOnTooltip, FilterNeedsOffTooltip, NeedsEmptyLabel, NeedUnavailableLabel ({0} = defName) and NeedUnavailableTooltip. A new GetFilterNeedsTooltip(bool triState) helper follows the GetAssignEveryoneTooltip pattern.
    • 3 reworded values, in all three locales:
      • EnsureWorkerAssignedOnTooltip and MinWorkerNumberTooltip gain "pawns blocked by the needs filter are never assigned" (AC-41).
      • AvailablePawnsTooltip gains "the needs filter is not applied to this preview" (AC-40, PRD D2).
    • Reused unchanged: WorkTypeRuleUndefinedSettingTooltip, WorkTypeRuleUndefinedSectionTooltip, WorkTypeRuleDisabledSettingTooltip, and Common's Actions.Add / Actions.Delete.
    • Each locale ends with the same 55 Settings.WorkTypes.* keys.
  5. Available pawns preview: the list is unchanged (PRD D2). Only its tooltip is reworded.

Consequences

Positive

  • No dependency on Common internals, so internal changes in Common cannot break the section.
  • Consistent with the existing tri-state rows and with Common's capacity rows: the same slider, delete glyph and Add label.
  • Unresolved entries are visible and removable. Common's capacity section hides them, so this improves on the precedent.
  • The add-menu selection and sorting logic can be unit-tested through the fake def provider.

Negative

  • The section is a labelled box with a checkbox row, not Common's inline toggle header, so it looks slightly different from the Allowed workers sub-sections.
  • The button reads the generic "Add", not "Add need" (accepted by the user).
  • The slider of an unresolved entry is still editable even though the entry has no effect.
  • The ChineseSimplified translation is best-effort (PRD D5). The reworded keys change existing Russian and Chinese text.
  • FloatMenuOption.tooltip is unverified until implementation. The fallback above keeps AC-31 reachable.

Alternatives considered

  • A local copy of DoToggleableSectionHeader, rejected because the editor already uses checkbox rows for tri-state fields, and a copy of an internal Common helper adds code with no requirement behind it.
  • Reflection into Common internals, rejected as fragile across Common updates: with Private=False, a change surfaces as a MissingMember error at runtime.
  • Hiding unresolved rows (Common's behaviour), rejected because it violates AC-35: such an entry could never be deleted.
  • A label-only row for unresolved entries, rejected because it adds a second row layout for a rare case.
  • A new "Add need" key, rejected by user decision (2026-09-29) in favour of Common's public "Add".

Related ADRs

  • ADR-0006: the fields this section edits.
  • ADR-0005: the key-addition precedent. This ADR departs from it by translating the Russian and Chinese values instead of shipping English placeholders (PRD D5), and by skipping the legacy locale folders.
