Work Manager — Sprint 002 PRD (Work-Type Needs Filters)

5 goals 8 stories 49 AC 9 non-goals updated 2026-09-29

Problem

WorkManager assigns work types by skill, passion, schedule and allowed-worker filters, but it ignores pawn needs. A pawn can stay on Mining under an overhead-mountain roof until its Outdoors need falls to "cabin fever" (−5) or "trapped / entombed underground" (−7 / −9), and until rough rock and rubble push its Beauty need down to "unsightly" / "ugly" (−5 / −10). The player has no way to say "do not assign this work type to a pawn while need X is below Y%". The only workaround is to set priorities by hand, and WorkManager overwrites them on its next update. See audit.md (Background research R-3, R-4) and sprint.md.

Goals

  1. G1

    Let the player block a work type for a pawn while any chosen need is below a per-need threshold (0–100%). This works for any need and any work type.

  2. G2

    Make the needs block absolute. No assignment path assigns a need-blocked pawn, including EnsureWorkerAssigned / MinWorkerNumber and the dedicated-worker fail-safe.

  3. G3

    Fit the needs filter into the existing rule model. It inherits from the default rule, is saved and loaded with the other rule settings, is edited in the work-type rules UI and is shown in the rule summary.

  4. G4

    Change nothing for players who do not configure the filter. No needs rules ship by default, older settings load unchanged, and assignments are identical while the filter is off.

  5. G5

    Make the feature robust and maintainable. Absent needs and needs from removed DLCs or mods never break evaluation. All UI text is localized in the three 1.6 locales. The logic is unit-tested, and the research on needs mechanics is documented as design background.

User stories

Mod player (colony manager) 7
  • as a mod player, I want to add any need, each with its own threshold, to a work type's rule, so that pawns whose need is below that threshold are not assigned that work type (e.g. Mining with Outdoors and Beauty). (G1; AC-1, AC-13…AC-20, AC-22, AC-27, AC-30…AC-36)
  • as a mod player, I want to set needs limits once on the default rule and have work-type rules inherit or override them, so that I configure colony-wide limits in one place. (G3; AC-1, AC-4, AC-5, AC-7, AC-8, AC-28, AC-29)
  • as a mod player, I want the needs block to take precedence over "ensure worker assigned" and "minimum workers", so that a need-blocked pawn is never forced onto the work type. (G2; AC-24…AC-26, AC-41)
  • as a mod player, I want assignments to follow my pawns' current need levels automatically, so that a pawn goes back to the work type once its need recovers, without my intervention. (G1; AC-21…AC-23, AC-38)
  • as a mod player, I want the rule summary and tooltips to describe the needs filter accurately, so that I understand why a pawn is or is not assigned. (G3; AC-37, AC-39…AC-41)
  • as a mod player with existing settings or a changing mod list, I want my settings to keep working when I update WorkManager or remove a DLC or mod that added a need, so that I get no errors and lose no configuration. (G4, G5; AC-2, AC-3, AC-6, AC-9…AC-12, AC-18, AC-35)
  • as a Russian- or Chinese-speaking player, I want the needs filter UI in my language, never as raw keys, so that I can use it. (G5; AC-42…AC-44, AC-49)
Maintainer 1
  • as the maintainer, I want the needs-filter logic unit-tested, the build warning-free and the needs research documented, so that the feature stays correct and future changes rest on verified RimWorld facts. (G5; AC-45…AC-48)

Acceptance criteria

Terms used below. Needs state: the tri-state of a rule's needs filter. Inherit uses the default rule's needs filter, Off means no needs filtering, and On filters by this rule's entries. Entry: one NeedDef plus a threshold. Need-blocked: blocked by the needs filter as defined in AC-13.

Design context

Resolved requirement decisions

The user approved these decisions on 2026-09-29. The binding scope decisions from sprint.md and .asd/project/decisions-log.md (2026-09-29 entries) also apply: a WorkManager-local filter, a strict below-threshold check, no shipped defaults, disable on block, an absolute block, the G-3 fail-safe option (a) and no hysteresis.

D1 Rule summary
The rule summary tooltip includes the needs filter (AC-39).
D2 Available pawns preview
The list is unchanged, and the tooltip states that the needs filter is not applied (AC-40). Reason: need levels change every update, and the preview shows the uncombined rule.
D3 Inheritance model
Tri-state Inherit / Off / On, mirroring PawnFilter's nullable filter flags. The default rule is normalised to Off, new rules start as Inherit, and older settings load as Inherit (AC-1, AC-4, AC-5, AC-7, AC-8, AC-10, AC-28).
D4 EnsureWorkerAssigned / MinWorkerNumber tooltips
Add only the statement that need-blocked pawns are never assigned (AC-41). The existing inaccuracy about the allowed-workers filter is left for a follow-up (see Non-goals).
D5 ru / zh text
The agent translates new and reworded strings into Russian and ChineseSimplified (AC-49). This intentionally departs from the ADR-0005 English-placeholder precedent, to avoid tooltips that mix two languages. The ChineseSimplified text is a best-effort translation.
D6 Add need list
All NeedDefs except playerMechsOnly needs and Authority, including needs with showOnNeedList = false. Needs already added are hidden. Sorted by listPriority (highest first), then by label (AC-30).
D6a Add button label
The add button reuses LordKuper.Common's existing public "Add" string instead of a new "Add need" key (AC-30). The user approved this during ADR approval.
D7 Initial threshold
50% for a newly added need (AC-32).
D8 Slider step
1% (AC-33).
D9 Unresolved entries
Shown with their defName and an "unavailable" marker, and removable (AC-35).

Skipped design steps

The UX-spec and design-system steps are skipped for this sprint. This follows the LordKuper.Common precedent: Common sprint 004, an IMGUI widget sprint, skipped them with the reason "IMGUI library, no web UI". WorkManager's settings UI is RimWorld IMGUI composed from Common primitives. The UI requirements live in the settings-ui acceptance criteria above (AC-27…AC-41) and in the sprint ADR.

Non-goals

  • Changing LordKuper.Common, including adding a needs dimension to PawnFilter.
  • Shipping needs rules for Mining or any other work type.
  • Lowering priority, instead of disabling the work type, for need-blocked pawns.
  • Hysteresis or latching (enter-low / exit-high) of the needs block.
  • Actively restoring needs (sending pawns outside, scheduling recreation). The filter only withholds work.
  • Per-need threshold hints or thought-stage markers on the slider.
  • Restricting the dedicated-worker fail-safe to allowed workers (G-3 option (b)), and correcting the existing EnsureWorkerAssigned tooltip inaccuracy about the allowed-workers filter. Both are follow-ups.
  • Legacy 1.1–1.5 builds and locales.
  • Per-pawn exemption from the needs filter.
